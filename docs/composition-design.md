# 한글 조합과 구현 언어 초안

설계일: 2026-10-22. 제안 단계이며 제품 코드를 구현한 문서는 아니다. libhangul 실행 결과를 반영해 초기 Backspace 설계를 수정했다. 상세 근거·복잡도·호환성 검증은 [신뢰성 조사](composition-reliability.md)를 따른다.

후속 구현: [MVP 현황](mvp.md)에 이 설계에서 실제 구현한 부분과 남은 부분을 기록했다.

## 언어 선택

| 영역 | 제안 | 이유 |
|---|---|---|
| 한글 조합·언어 판단·세션·편집 계획 | Rust | 작은 상태와 버퍼의 소유권을 명시하고 같은 코어를 각 OS에 네이티브로 컴파일 |
| macOS 입력 연결·메뉴바·설정 | Swift | Apple API와 앱 수명 관리에 맞춘 얇은 연결부 |
| Windows 입력 연결 | Rust + windows-rs | Win32·COM 연결과 코어를 Rust에서 직접 호출 |
| 비교 실험·웹 데모 | 같은 Rust 코어의 WASM 빌드 | 동일 알고리즘을 키 trace로 비교 |

macOS에서는 Rust `staticlib`를 앱 안에 링크하고 작은 C ABI를 통해 직접 호출한다. 별도 서버·프로세스·JSON 왕복을 입력 경로에 넣지 않는다. ABI에는 세션 핸들, 고정 레이아웃 이벤트, 상태 코드, 길이가 명시된 바이트 버퍼를 사용한다. Rust `String`/`Vec` 내부 구조를 다른 언어에 노출하지 않으며, 버퍼 소유권과 유효 기간을 정한다. [Rust linkage](https://doc.rust-lang.org/reference/linkage.html), [타입 레이아웃](https://doc.rust-lang.org/reference/type-layout.html)

windows-rs는 Win32 호출과 Rust 타입의 COM 인터페이스 구현을 지원한다. TSF 입력기 연결에 필요한 인터페이스·등록·스레드 모델은 작은 Windows 실험에서 확인한다. 이 선택으로 Windows IME 통합이 이미 검증됐다는 뜻은 아니다. [Microsoft windows-rs](https://github.com/microsoft/windows-rs)

구현 언어만으로 성능을 단정하지 않고 실제 입력 경로를 측정한다. 성능 개선의 주된 수단은 증분 계산, 재할당 축소, 제한된 탐색과 직접 함수 호출이다.

## 한글은 검증된 두벌식 조합기를 기준으로 처리

현대 한글 두벌식을 먼저 지원한다. 처리 순서는 물리 키 → 자모 → 조합 상태 전이 → 표시할 음절이다. 언어가 한국어인지 판단하는 것은 별도 모듈의 책임이다. 조합기는 사전·문맥·OS를 알지 못한다.

첫 통합 실험은 **Rust 세션 + libhangul 조합 백엔드**로 시작한다. Rust로 조합기를 새로 작성하는 것은 선행 조건이 아니다. 라이브러리의 좁은 C API를 감싸고, native 통합과 언어 판별을 먼저 검증한다. 최종 제품에 포함할 백엔드는 라이선스·패키징 조건까지 확인해 확정한다.

조합 상태는 빈 상태, 단독 자모, 초성·중성·선택적 종성을 가진 음절이다. 복합 중성·종성은 테이블로 결합·분리한다. Shift가 있는 물리 키는 배열 해석 단계에서 별도로 매핑한다. Unicode 정규화만으로 키 입력 순서와 삭제 규칙을 대체할 수는 없다.

| 키 입력 | 한글 후보 | 전이 |
|---|---|---|
| `r` | ㄱ | 초성 준비 |
| `k` | 가 | 중성 추가 |
| `q` | 갑 | 종성 추가 |
| `t` | 값 | 종성을 ㅄ으로 결합 |
| `k` | 갑사 | ㅄ에서 ㅅ을 다음 음절 초성으로 이동 |
| Backspace | 갑ㅅ | 현재 조합 중인 `사`의 ㅏ를 삭제; 앞의 `갑`은 유지 |

위 결과는 libhangul 기본 두벌식으로 실행해 확인했다. 초기안의 `갑사 → 값`은 일반 삭제와 입력 이력 되감기를 혼동했으므로 폐기한다. 붙여넣은 `갑사`나 이미 조합이 종료된 호스트 텍스트는 호스트의 삭제 계약을 따른다.

완성형 한글은 다음 표준 식으로 인코딩한다. 각 인덱스는 Unicode가 정의한 순서를 사용하며 종성 0은 종성 없음이다.

```text
codepoint = 0xAC00 + ((초성 인덱스 × 21) + 중성 인덱스) × 28 + 종성 인덱스
```

이 식은 음절을 문자로 표현하는 규칙이다. 키 입력의 복합 모음 결합·받침 이동·Backspace 규칙은 별도의 상태 전이로 구현해야 한다. [Unicode 한글 조합 규격](https://www.unicode.org/versions/Unicode17.0.0/core-spec/chapter-3/)

매 키마다 문장 전체를 재조합하지 않는다. 현재 조합 상태와 변경되는 끝부분만 갱신한다. 한글 조합의 상태 전이 자체는 고정 테이블과 작은 상태로 O(1)을 목표로 한다. 문맥 판별과 결과 문자열 전체의 비용까지 O(1)이라고 부르지는 않는다.

## 삭제·자동 변환 취소·호스트 확정은 다른 동작

입력 세션은 원래 키열뿐 아니라 **음절 경계와 조합 상태**를 소유한다. `rkqtk`에서 마지막 키만 제거해 `rkqt`를 처음부터 재생하면 `값`이 되어 삭제 결과 `갑ㅅ`과 달라진다. 후보를 다시 만들 때도 확정 경계가 있는 조합 기록을 보존한다.

Backspace는 현재 음절을 조합기의 삭제 API로 수정한다. 현재 음절이 없고 세션이 보유한 미확정 토큰 접두부가 있다면 그 마지막 글자를 지운다. 세션 소유 텍스트도 없으면 호스트에 맡긴다. 자동 변환 전체를 취소하는 undo는 별도의 `UndoJournal`이 담당하며 일반 삭제에 섞지 않는다.

조합기가 반환하는 `commit`은 음절 단위의 완료이고, 앱에 보내는 `CommitText`는 입력 세션 단위의 확정이다. 자동 한영 판단을 위해 한 단어를 marked text로 유지한다면 조합기의 완료 음절은 토큰 접두부에 쌓고, 공백 등의 경계에서만 호스트에 확정한다. 이 두 완료 시점을 구별하는 책임은 `CompositionSession`에 둔다.

기록은 현재 수정 가능한 구간으로 제한한다. 오래된 기록의 폐기나 긴 토큰 제한은 자동 재판단·되돌리기 범위를 줄이는 정책이며, 기본 한글 조합을 중단하는 정책이 아니다. 포커스·커서 이동·붙여넣기는 플랫폼 세션에서 별도 경계로 전달한다.

## 한영 자동 선택은 조합 위에서 수행

하나의 원시 키열을 영어 그대로 읽는 후보와 한글 조합 후보로 함께 유지한다. 예를 들어 `rkqt`에는 영어 `rkqt`와 한글 `값` 후보가 생긴다. `githubdp`에는 영어 접두어 `github`와 한글 접미어 `에`를 묶는 후보도 필요하다.

1. 현재 조합과 접두어 사전 위치를 한 키만큼 갱신한다.
2. 영어·한글·가능한 혼합 분절 후보의 바뀐 특징을 평가한다.
3. 확실하면 변환하고, 애매하면 유지하거나 다음 경계까지 보류한다.
4. 공백·Enter에서는 제한된 최근 문맥을 다시 평가한다.
5. 표시 목표와 실제 표시의 차이만 편집 계획으로 반환한다.

한글 받침이 이동하면 앞 음절도 바뀌므로, n-gram 누적 점수는 단순 추가만 하지 않고 영향받은 끝부분의 점수를 제거·재계산한다. 한국어 음절 쌍과 영어 삼중항의 변경 범위는 다르게 관리한다. 후보 수와 문맥 길이를 제한하고, 상한에 도달하면 확신 없는 강제 변환을 피한다.

## 코드 책임과 비용 관리

| 책임 | 대표 함수 형태 | 반환 의미 |
|---|---|---|
| 배열 해석 | `map_key(event)` | 자모·기호·제어키 |
| 한글 전이 | `composer.process(key)` / `composer.backspace()` | 키 소비 여부, 완료 음절, 현재 조합 |
| 조합 수명 | `update_composition(session, result)` | marked text 갱신·호스트 확정·통과 동작 |
| 후보 평가 | `score_candidates(candidates, evidence)` | 후보별 점수와 근거 |
| 변환 결정 | `choose_action(scores, policy)` | 유지·보류·교체 |
| 편집 계산 | `plan_edit(shown, target)` | 최소 접미사 변경 |
| 실제 반영 | 플랫폼 `apply_edit(plan)` | 제출·관찰 확인·거부·부분 적용 |

진입점은 위 함수들을 실행 흐름 순서로 직접 호출한다. 복구 기록과 정책 경계는 이름 있는 별도 함수로 드러내고, 한 줄 전달만 하는 추상화는 만들지 않는다. 코어 내부에서 trait 객체와 동적 디스패치를 기본값으로 사용하지 않는다.

- 고정 자모 테이블과 예약한 세션 버퍼로 일반 타건 경로의 재할당을 최소화한다.
- 사전·통계는 준비된 불변 데이터로 공유한다. 키마다 로딩·락 경합·파일 I/O를 만들지 않는다.
- 한 키 처리는 해당 세션의 한 실행 경로에서 순서대로 수행한다. 사전 준비·갱신만 별도 작업으로 한다.
- 세션별 상태를 유지해 입력 대상 전환 때 전체 history 재생을 피한다.
- 표시할 부분만 인코딩하고 반환한다. 일반 타건에서 전체 문장을 매번 UTF-8/UTF-16으로 바꾸지 않는다.

## 먼저 검증할 것

기준 라이브러리에서 11,172개 현대 한글 음절의 조합과 삭제, 복합 받침 이동 등 6개 trace를 실행했다. 이것은 Amu 구현의 테스트 통과가 아니다. 독립 조합기를 작성한다면 같은 trace를 양쪽에 실행하고 매 단계의 조합·완료·키 소비 결과를 비교한다. Unicode 음절 왕복만 통과해도 타이핑 전이가 맞는 것은 아니다.

macOS에서는 InputMethodKit으로 조합 중 텍스트와 확정 텍스트를 구별해 전달하는 실험을 먼저 한다. 입력 소스로 Amu를 한 번 선택한 뒤 내부에서 한영을 자동 판단한다. 한 단어를 조합 중으로 유지하는 정책은 Firefox의 일반 입력창·contenteditable, 터미널 등에서 별도 검증한다.

성능은 조합기 단독, 전체 언어 판단, OS 화면 반영을 나눠 측정한다. 동일 입력에서 지연이 줄어들고 오변환·수정 누락·편집 손실이 증가하지 않아야 개선으로 인정한다.
