# 후보 비교와 모호한 입력의 정책

`돼지갈비 vs 소고기`의 `vs`와 `ㄹㅇ`의 키열 `fd`는 모두 두벌식 자음 두 개로 해석할 수 있다. 자음 쌍이라는 형태만으로 초성 의도를 확정하면 정상 영문까지 바뀐다. 앞 단어가 한글이라는 사실만으로도 구별할 수 없다.

## 현재 실행 흐름

1. `Decoder`가 전체 한글·전체 영문과 가능한 초성·한영 혼합 후보를 만든다. 조합은 libhangul이 담당한다. 초성과 반복 자모도 점수를 가진 후보로 비교하며 조기 반환으로 승리시키지 않는다.
2. `english`, `korean_evidence`, `korean_statistics`, `initial_statistics`가 철자·조합·통계 근거를 제공한다. 초성은 형태에 맞을 때만 후보로 생성한다. [초성 통계](../models/initials/README.md)의 log odds에 0.75를 곱해 영문 후보 대비 비용 차이를 만들며, 기존 단어·연결 철자·열린 모음 접두부의 영문 근거에는 초성 비용 4.0을 더한다. 같은 쌍의 반복으로 통계 근거를 중복 계산하지 않는다.
3. `selection`이 최상위 두 후보와 최선의 전체 후보를 보관하고 선택한다. 수동 선택용으로 최선의 혼합 후보도 별도로 보관한다. 후보 비용이 낮을수록 유리하다. 점수와 그 차이는 휴리스틱이며 보정된 확률이 아니다.
4. `Session`이 선택한 후보를 조합 영역에 표시한다. 공백에서는 보이는 문자열을 그대로 확정한다. 의미를 추측해 이전 확정 단어를 다시 쓰지 않는다.

### 입력 중 표시의 연속성

키 입력 도중에는 아직 완성되지 않은 후보도 비교한다. `KoreanEvidence`는 직전 한글 해석에서 libhangul이 새 초성을 기다리는 상태를 확인한다. 앞 음절이 관측되고 다음 초성 연결이 기존 음절 bigram에 있거나 된소리 Shift 근거가 있을 때 미조합 비용을 면제한다. 온전한 영문 근거가 경쟁하면 이 유지를 적용하지 않는다. 영어 뒤의 미완성 한글에는 영문 접두부의 철자·단어·식별자·대문자 근거도 요구해, 길이만으로 잘못 나눈 경계를 유지하지 않는다.

`english`는 열린 철자 접두부를 완성 철자와 구분한다. 기존 영문 표시가 이어지는 동안 미완성 한글과 경쟁할 수 있지만, 완성 한글을 열린 영문 할인만으로 밀어내지 않는다. `lo`처럼 두 글자이고 한글로 완성되지 않는 접두부도 뒤를 붙여 온전한 영문 철자가 되면 연결 근거를 인정한다. `lock`이나 특정 접미부를 등록하는 규칙은 아니다.

`DisplayPolicy`는 이미 표시한 영문 키를 약한 한글 후보로 바꾸는 비용을 키당 0.75, 최대 2.0으로 계산한다. 근거가 있는 전체 한글·한글 접두부, 원문 영문 복구, 초성은 면제한다. `selection`이 이 비용을 포함해 순위를 계산하지만, 비용을 넣기 전과 승자가 달라지면 `Ambiguous`로 남긴다. `Session`이 직전 해석을 전달하며 수동 선택·삭제·고정 모드의 계약은 유지한다. 다음 키를 기다리는 타이머나 공백 시 숨은 재판독은 없다.

초성 표현의 반복이 한 키 덜 입력된 단계도 직전 초성 후보의 연속으로 비교한다. `ㄱㅅㄱ`를 영문으로 되돌렸다가 `ㄱㅅㄱㅅ`로 바꾸지 않는다. 기존 후보와 점수를 비교하므로 임의 자음 문자열을 전부 초성으로 만드는 규칙은 아니다.

[키 단위 비교 보고서](../research/typing-stability.md)는 최종 정확도·매 키의 표시 정확도·반복 전환·지연을 분리하고, 아직 실패하는 사례도 집계한다. `mise run core:stability`로 재현한다.

### 완성된 한글처럼 보이는 영문

`query`는 libhangul에서 `볃교`로 완전히 조합된다. 조합 가능 여부와 `교` 한 음절의 관측만으로 전체 한글 후보를 지지하지 않는다. 관측된 음절이 하나 이상 있고 **모든 음절**이 관측 또는 결합 근거를 가져야 한다. 미관측 받침 음절은 초성·중성과 중성·종성 결합이 각각 관측되면 보완한다. 이 방식으로 드문 `촘`이 들어간 `촘촘히`도 보존한다. 미관측 열린 음절에는 받침이라는 추가 근거가 없으므로 같은 보완을 적용하지 않는다. 명시적인 한글 Shift 근거는 기존대로 유지한다.

영문에서는 `qu`의 `u`를 별도 모음으로 세지 않아 모음 비율 때문에 연결 철자를 배제하지 않는다. 완성 한글과 경쟁하는 영문 접두부 뒤에 새 한글 음절이 붙으면, 기존 seed에서 관측한 문자 연결도 확인한다. 단지 가능한 끝자음군이라는 이유로 뒤의 한글을 영문에 흡수하지 않는다. 이 규칙은 기존 영문 seed와 음절 U/B 통계를 유지한다.

### 영문 어간 뒤의 약어와 한글 경계

`graphql → graph비`처럼 끝부분이 우연히 한글 한 음절이 되는 경우, 발음 가능한 어간에 자음 약어가 붙은 영문 후보도 비교한다. 어간 3키 이상, 약어 2~6키를 검사하며 `graphql`, `sql`, `db` 같은 문자열을 등록하지 않는다. `english`가 철자와 비용을 제공하고, `english_identifier::IdentifierProbe`가 별도 libhangul 조합기로 경쟁하는 한글 해석을 확인한다. 실제 입력·삭제 상태를 재조합하지 않는다.

이 추가 근거는 약어 키가 한글 한 음절로 완성되지만 조사·어미 시작으로는 거의 관측되지 않는 경우에 한정한다. 기존 GSD train의 J/E 형태소 태그에서 집계한 [음절별 시작 비용](../models/korean/README.md)이 상한 6에 도달할 때 사용한다. 전체 영문 비용은 기존 비용과 `어간 길이×1.1 + 약어 길이×1.5 + 1.0` 중 작은 값이다. 어간은 기존 연결 철자 또는 일반 단어 형태를 만족해야 한다. 자모가 남거나 여러 한글 음절이 완성된 부분을 무조건 약어로 할인하지 않는다. 따라서 `packet를`, `florp고`, `rust한글` 같은 기존 혼합 입력을 이 근거만으로 영문에 흡수하지 않는다.

혼합 경계에서도 첫 한글 음절까지가 같은 영문 식별자 근거를 가지면 해당 음절의 시작 비용을 더한다. 뒤에 새 한글을 입력해도 `graph|비를`로 되돌아가지 않고 `graphql|를`, `graphql|한글`을 비교할 수 있다. 후보를 삭제하지 않으므로 실제 의도가 `graph비`라면 수동 선택으로 고를 수 있다. 전체 한글 후보의 보호와 모호함에 대한 선택 정책은 유지한다.

개발 회귀는 실사용 식별자와 미등록 `florpdb`, `vexql`, `plintdb`, `norgql` 등 10종, 한글 접미 구간 9종, 문맥 5종을 포함한다. 별도 EWT test 12,060건의 수정 전후 비교에서 11,174→11,207건으로 개선되었고 새 실패는 없었다. GSD test 28,875건의 출력은 전부 동일했다. 기존 오류까지 해결됐다는 뜻은 아니며, test 자료를 비교한 개발 결과를 블라인드 정확도로 표현하지 않는다.

## 확신이 부족할 때

| 상황 | 표시·확정 정책 | 언어 이력 |
|---|---|---|
| 초성·혼합 후보가 전체 후보보다 0.75 미만 유리함 | 전체 후보를 보존. 초성과 자음 영문이 경합하면 대체로 원문 영문을 유지 | 반영하지 않음 |
| 두 혼합 경계 모두 전체 후보보다 충분히 유리하지만 서로 비슷함 | 가장 낮은 비용의 경계를 표시하고 모호함과 차선 후보를 유지 | 반영하지 않음 |
| 전체 한글·전체 영문이 서로 비슷함 | 최저 비용의 전체 후보를 유지. 이미 유효한 한글 조합도 보존 대상 | 반영하지 않음 |
| 최상위와 차선 비용 차이가 0.75 이상이고 표시 비용 전후의 승자가 같음 | 최저 비용 후보 선택 | 선택 언어를 반영 |
| 명시적 한글·영문 모드 | 사용자가 고른 모드 | 선택 언어를 반영 |
| 현재 단어의 수동 후보 선택 | 사용자가 고른 후보와 혼합 경계를 단어가 끝날 때까지 유지 | 선택 언어를 반영; 단어별 사전은 만들지 않음 |
| 삭제로 해석이 고정된 토큰 | 실제 libhangul 삭제 상태와 현재 해석을 보존 | 새 판독 근거로 반영하지 않음 |

문맥은 네 단어의 제한된 언어 경향이다. 모호한 확정도 빈 표 하나를 넣어 오래된 이력을 밀어내지만 한글·영문 어느 쪽에도 표를 주지 않는다. 문장 의미나 주변 문서를 읽지는 않는다. 초성 통계에 앞선 언어의 표를 더하지 않아 `hello ㄹㅇ`와 `한글 vs`를 같은 근거로 판단한다.

`Session::interpretation()`은 `Idle / Supported / Ambiguous / Explicit / Edited`, 차선 후보의 언어, 최상위 두 후보의 비용 차이를 제공한다. 전체 후보 보존 정책을 적용한 경우 이 비용 차이는 화면에 선택된 후보의 우위를 뜻하지 않는다. 삭제 후에는 차선 후보와 점수 차이를 폐기해 오래된 진단을 재사용하지 않는다. C ABI와 OS 조합 출력의 레이아웃은 유지한다.

## 검증 기준

- [문장 fixture](../crates/amu-core/tests/fixtures/sentences.tsv)는 실제 의도한 문자열을 정답으로 둔다. 이전 단어가 영어라는 이유로 `ㄹㅇ`의 정답을 `fd`로 바꾸지 않는다.
- 모든 자음 쌍을 한글로 바꾸라는 생성 테스트는 제거했다. 형태만으로 의도를 정답 처리하지 않는다.
- [초성·영문 회귀 자료](../crates/amu-core/tests/support/initials.rs)의 영문과 초성 의도를 같은 다섯 문맥에서 확인하고 대문자·삭제·재입력·공백·모드·버퍼 경계를 함께 검사한다. 이 자료는 개발 회귀이며 블라인드 정확도가 아니다.
- 아직 모호한 `ㄴㅈ`, `ㄴㅎ` 의도는 평가에서 실패로 집계한다. 원문 보존 정책이 정상 동작해도 의도를 맞혔다고 세지 않는다.
- 한국어 GSD test의 9,625토큰×3문맥을 수정 전후 토큰별로 비교한다. 기존 오류가 남아 있으므로 새 회귀 0건과 전체 정확도 100%를 구분한다.
- EWT test의 자음 영문 어형을 모두 소문자화해 검사하고 train에 없던 어형을 따로 보고한다. 일반 영어 test에서의 이 의도는 영문으로 고정하며, 실패 사례를 초성 정답으로 바꾸지 않는다.
- 같은 EWT test의 4~64자 ASCII 영문 어형 전체도 빈 문맥·한글 뒤·영문 뒤에서 비교한다. 전체 결과와 단어 힌트에 없는 부분집합, 새 실패와 개선을 분리한다. 이 자료를 보고 수정한 결과는 블라인드 평가로 표현하지 않는다.
- `query/queue/angry`는 각 키에서 조기 확정이 없는지, 완성 전에 표시가 조합 또는 원문 후보인지, 완성 후 원문 보존·전부 삭제·재입력·확정이 되는지 검사한다. 초기의 `qu → 벼` 같은 모호한 중간 표시를 영문 인식 성공으로 세지 않는다.
- 코어 검사와 합성 AppKit 검사는 외부 앱의 실제 시스템 입력기 검증을 대신하지 않는다.

## 수동으로 현재 단어 선택

macOS 자동 모드의 `Ctrl+Shift+Space`는 공통 코어의 `Input::CycleReading`을 호출한다. 전체 영문 → 기존 탐색에서 생성된 최선의 혼합 후보(있을 때) → 전체 한글 순서로 순환한다. 두벌식 자음 키만 있다면 한글 자리에 초성 후보를 둬 `rt`를 `ㄱㅅ`으로 선택할 수 있다. 수동 초성 선택에는 자동 판독의 표현 형태·빈도 제한을 적용하지 않는다. 모든 분절 경계를 나열하지 않으며 자동 탐색이 생성하지 않은 혼합 경계는 이번 후보에 포함되지 않는다. 자동 판독의 점수·문맥 정책은 그대로다.

`Session`은 수동 선택과 지속 모드를 별도로 소유한다. 수동 선택은 `Explicit`이며 다음 키에도 자동 점수로 뒤집지 않는다. 혼합 후보는 선택한 경계에 이어 입력하고, 초성 뒤 모음은 정상 한글 조합으로 돌아간다. 공백·기호·Finish·reset·모드 변경·버퍼 한도 확정에서 단어 선택을 해제한다. 고정 한글·영문 모드와 빈 조합에서 교정 명령은 소비만 한다. 키 반복 이벤트는 macOS 연결부에서 소비해 후보가 연속으로 돌아가지 않게 한다.

영문·초성 삭제는 남은 원시 키를 보유하므로 재선택할 수 있다. 한글 자모 삭제는 실제 libhangul 경계를 보존하면서 원시 키열을 폐기한다. 이 상태에서 재해석하면 `갑ㅅ`이 `값`으로 합쳐질 수 있으므로, 전체 키열이 남아 있지 않은 조합은 재선택하지 않는다. 혼합 단어의 한글 부분 삭제도 같다. 영문 접두부만 남을 때는 다시 재선택할 수 있다. 수동 초성 뒤에 모음을 붙이면 마지막 초성만 이어 조합해 `ㄱㅅㅋ → ㄱㅅ카`를 보존하고, 이 별도 경계도 원시 키 재해석으로 합치지 않는다. 이미 확정한 단어·커서 앞 문서는 읽거나 수정하지 않는다.

`Ctrl+Shift+F1/F2/F3`는 자동·한글·영문 모드를 직접 고른다. 모드 전환은 현재 표시를 먼저 확정하며, 고정 모드는 공백 뒤에도 유지한다. macOS 입력 대상 활성화 시 자동 모드로 초기화하고 이전 버전의 저장된 모드 설정은 읽지 않는다. Playground는 창을 떠날 때 자동으로 돌아간다. 모드 표시와 키 해석은 Swift가 맡고 후보 선택은 Rust가 맡는다. 보안 입력에서는 수동 명령도 원래 이벤트 그대로 전달한다.

검사는 `dia browser`, 미등록 영문 키열, 동일한 키의 `fd/ㄹㅇ`·`vs/ㅍㄴ` 의도, 정상 한글, 혼합 후보, 삭제 후 경계, 확정·reset·버퍼 한도, C ABI, AppKit 재진입·키 반복·보안 입력을 포함한다. 이 검사를 통과했다는 사실은 외부 브라우저에서 단축키를 가로채지 않는다는 보장은 아니다.

## 비용과 남은 한계

초성 근거 조회는 O(1), 형태 검사는 O(n)이다. 후보 비교기는 최상위·차선·전체·혼합 후보만 보관하므로 추가 공간 O(1)이며, 기존 분절 탐색의 키당 O(n²) 시간·세션 O(n) 공간 상한을 유지한다. 수동 교정 시 같은 탐색을 한 번 실행하고 최대 세 후보를 순환한다. 토큰은 최대 64키이며 모델은 세션 준비 시 한 번 읽는다. 식별자 근거는 최대 다섯 약어 분할점만 추가로 확인하므로 전체 탐색의 점근 복잡도는 같다. 별도 조합 context 하나와 고정 음절 시작 비용 배열 약 44 KiB를 추가로 사용한다. 키 처리 중 네트워크·디스크 I/O·입력 로그는 없다.

일반 말뭉치의 문자 쌍 통계는 실제 채팅 의도나 문장 의미 모델이 아니다. 같은 키열의 두 의도, 자료가 부족한 초성·약어, 입력 도중 후보가 바뀌는 현상은 여전히 남는다. macOS에서는 `fd`를 입력한 뒤 수동 교정으로 영문을 선택할 수 있다. 확정 후 변환 취소와 Windows의 현재 단어 교정 키는 아직 없다.
